# Lab 5：并发同步与死锁检测

## 实验内容

这一章在已有线程、互斥锁和信号量的基础上加入死锁检测。系统调用打开检测后，线程在一次加锁或 `P` 操作将要阻塞前，内核先判断当前资源状态是否还存在一条能让所有线程结束的执行顺序。如果已经不存在安全序列，本次申请返回 `-0xdead`，由用户程序决定如何释放已持有的资源。

## 资源状态的记录

检测状态放在进程控制块中，因为同一进程的线程共享互斥锁和信号量。内核分别保存每个线程已经占有的资源和正在等待的资源；新建线程或同步对象后，矩阵会按当前数量扩展。正常取得资源后增加 allocation，`unlock` 或 `up` 时减少；如果申请需要等待，则先登记 request，检测通过后才进入阻塞队列，唤醒时再把 request 转为 allocation。

互斥锁的资源总数固定为 1。信号量则额外记录创建时的容量，用“总容量减去当前分配量”计算可用资源。这里不能直接采用信号量内部的即时计数：`up` 唤醒等待线程后，到该线程真正恢复运行并完成记账前存在一个很短的窗口，此时令牌已经预留给它，内部计数为 0，但从安全性分析的角度，该线程仍然可以取得令牌、运行并归还资源。第一次实现用即时计数，恰好在这个窗口把无死锁的 `sem2` 用例误判了，改用固定容量后结果稳定。

## 安全性判断

算法从当前 Available 得到工作向量 `Work`。每轮寻找 request 不超过 `Work` 的未完成线程，假设它能够执行结束，再把它已经占有的资源加入 `Work`。不断重复，若所有活动线程都能被消去，状态就是安全的；若某一轮没有线程可以继续而仍有未完成线程，就认为发生死锁。

屏障信号量是容易误判的一种情况。主线程可能暂时拿走全部令牌，子线程都在等待，但主线程本身没有新的资源请求，因此它可以先完成并归还令牌，检测算法会把这一状态判断为安全，而不是简单地把“当前没有令牌”当成死锁。

## 验证结果

使用课程指定的 Rust 工具链构建内核和用户程序，在 QEMU 8.2.2 与仓库提供的 RustSBI 上运行官方 `ch8.py`。互斥锁重复加锁、信号量循环等待、无死锁信号量场景以及线程、条件变量、管道和前置章节回归测试全部通过，最终结果为 `25/25`。
